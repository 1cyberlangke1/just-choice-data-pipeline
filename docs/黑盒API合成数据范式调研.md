# 黑盒 API 合成数据范式调研

> 范围：只谈「用在线黑盒 API（OpenAI 兼容端点 / 第三方中转 / 免费档）批量造选择题数据集」
> 这一件事。不涉及预训练语料清洗、模型蒸馏、SFT 配方。
> 目的：给本项目的 workflow 设计与判别器选型提供依据。
> 调研日期：2026-09-24。文中标「实测」的条目是本仓库自己在 NVIDIA NIM 上跑出来的，
> 其余为公开文献/文档，来源见第 8 节。

## 0. 一句话结论

黑盒 API 只能做三件事：**写文本**、**给标签**、**当裁判**。这三种能力对应三条可靠性递减的路线。
凡是能用代码算出来的答案，就绝不让模型给——这是本项目所有决策的总纲。

## 1. 三条主轴

任何「用 API 造数据集」的方案，都是这三根轴的取值组合：

| 轴 | 取值（从左到右可靠性递减） |
|---|---|
| 答案从哪来 | 代码构造 → 标签先行注入 → 从素材抽取 → 模型直接判断 |
| 多样性从哪来 | 标签维度组合 → 模板/问法枚举 → 换采样温度 |
| 谁判对错 | 构造即正确 → 程序往返校验 → LLM 判别器 → 人工抽检 |

三条轴互相独立：可以「答案由代码构造 + 多样性靠 tag 枚举 + 完全不判」（迷宫），
也可以「答案由模型判断 + 多样性靠温度 + 全靠判别器兜底」（主观风格题，最脆弱）。
**先在这张表上选好坐标，再写代码**；选错坐标的代价是数据全废。

## 2. 范式清单

### 2.1 自举自生成（Self-Instruct）

做法：175 条人工种子指令 → 模型生成新指令 → 过滤（ROUGE 去重 + 规则）→ 加回任务池 → 迭代。
原始工作产出 52k 指令 / 82k 实例。

- 适用：开放域「指令」，答案本来就是自由文本。
- **对本项目部分不适用**：我们的答案是闭集整数/布尔，自举只会放大「答案由模型决定」这个最不可靠
  的环节。
- 值得抄的是它的**闭环**：「生成 → 过滤 → 回池」。本项目把这一环拆成
  `validate → rejected.jsonl` 与 `verify → quarantine.jsonl`。
- 已知坑：迭代几轮后多样性塌缩（模型只会生成像种子的东西）；ROUGE 对中文近似无效。

### 2.2 进化式改写（Evol-Instruct）

做法：对已有题目施加固定的**改写算子**（加约束 / 换更罕见的条件 / 增加推理步数 / 塞入错误参考 /
提高复杂度），用模型重写后再让模型作答。参考实现里算子就是一份字符串列表加 `random.choice`。

- **对本项目**：这是「最小对（minimal pair）」的通用化。迷宫 workflow 用「改 spec 一个属性 →
  重渲染 → 答案自动重算」实现了同一思想的无模型版本。
- 坑：改写会破坏答案的可判定性。**改完题必须重算金答案，不能让模型顺手改答案**。

### 2.3 无种子自举（Magpie）

做法：只喂 instruct 模板的前缀（到 user 位置为止），让对齐过的模型自己续出一个用户问题，
从模型里「抽」出指令。原工作产出 400 万条。

- **对本项目不适用**：它造的是「问题文本」，我们要的是「state + 题 + 金答案」三元组，
  且答案必须可验证。
- 唯一可借鉴的点：多样性来自采样而非提示词工程——但这与本项目「多样性必须可复现」冲突。

### 2.4 标签先行 + 特征注入（本项目的主力）

做法：**先定标签，再按标签注入可观察特征，模型只负责把特征写成自然语言**。

- 为什么比「让模型判断」可靠：**标签是输入，不是输出**。模型把文本写坏只会让题目变差，
  不会让金答案变错。
- 本项目对应：PLAN 3.2 的「特征注入式」+ 3.3 的 tag 笛卡尔积。官方出题守则把
  「这封邮件是垃圾吗」拆成 6 个原子 noul（索要凭据 / 意外奖励 / 时间压力 / 发件人身份不符 /
  链接域名不符 / 链接文字伪装），那份清单正好当注入模板。
- **前提条件（容易漏）**：注入的特征必须在成文后仍然可查。模型可能「写过头」，把没注入的特征
  也写进去，这时标签就错了。判别器的第一职责就是逐特征反查，见 4.2。

### 2.5 检索 / 知识图谱接地

做法：先从素材（KG 路径、检索到的段落）构造结构化上下文，再让模型按上下文出题。

- 参考：KNIGHT（KG 多跳路径 → 四选一 MCQ，用「答案可否由给定证据推出」当幻觉代理指标）、
  D-GEN（干扰项生成，用排序一致性与预测熵评估干扰项质量）。
- **对本项目**：这是「第二个 workflow」最现实的一条路，但没有真实语料是硬伤（见 6.2）。
- 关键实践：把「答案是否**只**由给定证据推出」当成一等判别指标，而不是事后想起来的补丁。

### 2.6 构造式（零模型）

做法：答案由生成算法保证，模型完全不参与。

- 本项目对应：迷宫 workflow。这是唯一「答案 100% 正确且零 token」的范式。
- 额外价值：它是**判别器的校准锚**——拿它喂判别器应该全过，误杀说明判别器太严。

### 2.7 回放缓存（Replay）

做法：把 `task_id → Draft` 缓存起来，重跑零成本。distilabel 等框架把缓存做进 pipeline。

- **对本项目**：缓存与进度必须分开（PLAN 3.1.5）。缓存是可选加速，进度是正确性所需，
  两者合并会导致「缓存命中但产物没落盘」这类无法对账的状态。

## 3. 多样性：怎么造出「不一样」的题

### 3.1 三个层次

| 层次 | 手段 | 可复现 |
|---|---|---|
| 结构层 | 标签维度组合（笛卡尔积 / 成对覆盖） | 完全可复现（枚举器是纯函数） |
| 文本层 | 同一组合换问法 / 换语言 / 换表述模板 | 可复现（模板 + 固定 seed） |
| 采样层 | temperature / top_p / 换 provider | 不可复现 |

结论：**多样性尽量往结构层和文本层压，采样层只当补充**。只靠 temperature 提多样性，
既不可复现，也没法做「留出」度量，更没法解释「这批数据为什么不一样」。

### 3.2 组合爆炸的处理

- 组合数 ≲ 10⁴：全枚举。
- 更大：**成对覆盖（pairwise / covering array）**，保证任意两维的取值组合至少出现一次。
- 本项目把「格式 case 枚举」与「tag 组合枚举」做成同一个实现（一个枚举 schema 维度、
  一个枚举 tag 维度）。

### 3.3 泛化性度量：三种留出，缺一不可

| 留出方式 | 含义 | 答的问题 |
|---|---|---|
| 组合留出 | 训练集里没出现过的标签组合 | 会组合吗 |
| 值留出 | 某一维出现过，但某个取值没出现过（如没见过的语言） | 会迁移吗 |
| 维度留出 | 整个维度在训练集里缺席 | 会泛化到新维度吗 |

只做 iid 切分等于没测泛化性。

## 4. 谁判对错：判别器与验证

### 4.1 确定性检查永远优先

顺序固定为：契约校验（结构）→ 往返校验（构造式）→ 特征核对（LLM）→ 人工抽检。
能用代码查的一律先查；LLM 判别器只处理「代码查不了」的那部分：措辞、可解性、干扰项质量。
把结构问题丢给 LLM 判别器，等于花钱买不确定性。

### 4.2 三条硬规矩

1. **要评测的模型不参与过滤**。用哪个模型过滤，就会系统性删掉它做错的样本，数据集会偏向它。
2. **判别器本身要被评估**。人工抽检的 `reviews.jsonl` 是金标准，用来算判别器准确率与漏杀率；
   判别器不是「装上了就对」的组件，它自己也有一份评测报告。
3. **构造式样本当校准锚**。已知 100% 正确的样本喂进去必须全过，误杀说明判据太严。

### 4.3 判别器的输出形态

存 `{verdict, score, reason, raw}`，不要只存 pass/fail。理由：pass/fail 无法区分「确定错」与
「不确定」，事后想调阈值时没有任何信息可用，只能重跑。

可参考的判据集合：

- KNIGHT 的 5 条：语法通顺、**唯一正确项**、选项互不重复、答案可由给定证据推出、主题相关；
- 教育测评方向的做法（SAC 2026 那篇）：一组 16 项左右的质量判据，含歧义性、干扰项吸引力、
  难度是否合适、是否只考察目标学习结果等；
- 落地建议：**多判据拆开问**，不要用一条「这题好不好」的 rubric。多视角判别器按需开启，
  每个视角独立给分。

### 4.4 已知偏置与对策

LLM-as-judge 的公开问题：位置偏置、对同一输出的回答不一致、过拟合到特定提示词或领域。

- 对策一：拆判据（不要一个 rubric 问「好不好」）。
- 对策二：温度 0，确定性输出。
- 对策三：换模型交叉验证，或对争议样本二次判。
- 对策四：判据里写死「名字只允许出现在提示词携带的段落里」，避免裁判脑补。

## 5. 黑盒 API 的工程现实

这一节全是「踩过才知道」的东西，与算法无关但与成败有关。

### 5.1 结构化输出：三档降级

| 档 | 机制 | 说明 |
|---|---|---|
| `json_schema`（strict） | 服务端约束解码，只允许 schema 合法的 token | 最稳；很多端点/中转不支持或只是忽略参数后返 200 |
| `tools`（function calling, strict） | 同一套约束解码，包在工具调用里 | 单形状抽取时不如上一档（多一个「选哪个工具」的路由决策会出错） |
| `md_json` | 提示词 + 本地抠 JSON + 校验 + 回喂重试 | 最兜底；模型可能干脆不吐 JSON |

关键事实：

- 官方文档明确 strict 模式是「模型训练 + 约束解码」两段式；**首次使用新 schema 有一次编译延迟**
  （典型 <10 秒，复杂 schema 可达 1 分钟），之后走缓存。所以「换 schema 很贵」是真的，
  schema 要稳定。
- **strict 只约束形状，不约束内容**。实测：提示词要数字、enum 只准 `banana` 这种矛盾下，
  `openai/gpt-oss-20b` 直接 `finish_reason=length`、`content=None`。
- 所以：**探测返 200 不等于服务端真强制了 schema；本地校验永远不可省**。

### 5.2 采样参数

- **永不发 `max_tokens`，也不给开关**。推理模型会先把预算烧在 reasoning 上，设小了直接「想一半被砍死」
  （实测 `max_tokens=8` → `content=None`、`finish_reason=length`）。
- `reasoning` / `reasoning_content` **单独存、不回喂**，否则等于把思考过程塞回上下文。
- 原始响应文本要留档（`Draft.raw_text`），出问题时这是唯一的证据。

### 5.3 限速、并发、退避

- 免费档和第三方中转普遍有 RPM / TPM 限制，而且**很多端点不返回 `x-ratelimit-*` 响应头**
  （实测 NVIDIA NIM 只有 `Nvcf-Reqid` / `Nvcf-Status`），拿不到官方口径。
- 对策：配置里的 RPM 只当**起点**，收到 429 就把 RPM 减半（自适应降速），冷却后逐步恢复。
- **并发与限速是两件事**，同时生效、取更严的那个：并发管「同一瞬间打太多」，RPM 管
  「一分钟内打太多」。
- 退避：429 / 5xx / 超时走指数退避 + 抖动；429 带 `Retry-After` 时**以服务端要求为准**。

### 5.4 多 key 与多 provider

- 多 key：**最少在途优先**调度（并发下比轮询均衡）；401/403 只废掉这个 key，不算 provider 故障。
- 多 provider：有序降级链，**全部不可用才停整批**。
- 风险：换 provider 等于换模型，**同一批内混模型会污染数据分布**。所以「一家到底」还是
  「全挂才停」必须在配置里显式选一个，并把实际来源记进 manifest 与每条样本的记账字段。
- 免费额度不会提前告诉你还剩多少，只能靠「熔断 + 记账 + 事后统计」倒推。

### 5.5 断点续跑

几乎所有自研 batch runner 最后都会写出同样四样东西：

1. 并发限制器（免得自己把自己 429 掉）；
2. 指数退避 + 抖动的重试；
3. 死信队列（永久失败的别卡住整条流水线）；
4. 持久化状态（部署 / OOM / Ctrl-C 之后不用从头再来）。

本项目对应 `progress.jsonl`：追加写、每行 fsync、**先写产物再写进度**。
「先写进度再写产物」会在崩溃时留下「进度说完成、产物没落盘」，而正着来最坏只是重做一条。

### 5.6 成本可观测

每次调用记 token / 延迟 / provider，**追加写且 fail-open**（记账本身出错绝不能影响主流程）。
有批处理折扣的端点（如 OpenAI Batch API 打五折）适合离线跑量，但它牺牲的是延迟。
另外：**先算清楚量再跑**，免费额度是最先被烧完的东西。

## 6. 已知失败模式

### 6.1 按「能不能事后发现」排序

| 失败模式 | 表现 | 事后能否发现 | 对策 |
|---|---|---|---|
| 标签污染 | 金答案本身就是错的 | 只能靠人工/判别器 | **别让模型定标签** |
| 特征泄漏或丢失 | 注入的特征被写没、或被多写 | 可程序查 | 判别器逐特征反查 |
| 幻觉接地失败 | 答案不能由给定素材推出 | 可程序查 | 要求答案必须可由素材推出 |
| 模板感 | 所有题一个句式 | 人眼可辨 | 结构层多样性 + 多问法 |
| 近重复 | 语义相同、措辞不同 | 需要嵌入 | MinHash / SemDeDup / SemHash |
| 分布漂移 | 中途换了 provider 或 model | 记账可查 | 每条草稿带 provider / model / mode |
| 多样性塌缩 | 迭代自举后只会生成像种子的 | 分布统计可查 | 别迭代自举，改用 tag 枚举 |
| 判别器偏置 | 系统性误杀某一类 | 人工金标准可查 | 用构造式样本当锚 |

### 6.2 「没有真实语料」意味着什么

没有真实语料时：

- 不能用「真实分布」对齐，只能用**结构化的真值规格**（spec）保证答案正确性；
- 不能用「与真实数据的相似度」当质量指标，只能用**内部一致性**（往返校验、特征核对、
  对称变换、确定性重跑）当质量指标；
- 因此**构造式与特征注入式优先**，纯判断式（模型给答案）最后考虑。

### 6.3 去重的量级

- 精确重复：一行哈希即可，成本可忽略。
- 近重复：MinHash + LSH（`char_ngrams >= 20` 可减少误报）能处理百万级；
  SemDeDup 用嵌入 + 聚类 + 组内余弦阈值；SemHash 用 Model2Vec 嵌入，实测 180 万条文本
  在 CPU 上约 83 秒。
- **跨切分去重必须做**，否则 train 与 test 有近重复，评测结果虚高。

## 7. 与本项目的对应

### 7.1 范式选型

| 范式 | 在本项目的位置 | 状态 |
|---|---|---|
| 构造式 | `workflows/maze`（答案由算法保证，零 token） | 已有 |
| 标签先行 + 特征注入 | 第二个 workflow 的首选（垃圾邮件、欺诈、意图…） | 待做 |
| 检索 / KG 接地 | 没有真实语料，暂缓 | 待定 |
| 自举自生成 | 只借「生成 → 过滤 → 回池」的闭环形状 | 部分采用 |
| 进化式改写 | 只借「最小对」思想（改 spec 一个属性） | 借思想 |
| Magpie 式无种子自举 | 不采用（答案不可验证、多样性不可复现） | — |
| 回放缓存 | 与进度分开实现 | 待做 |

### 7.2 工程侧现状

已完成（`src/jc/backend/`）：key 池负载均衡、限速、熔断、三档结构化输出降级、
多 provider 降级链、断点续跑（追加写 + 先产物后进度）、端点能力探测。

装配入口 `build_backend(config)` 已补上（key 只从环境变量读、可选开机探测、
是否允许混模型取自配置）。

尚未做：把 backend 接进 pipeline；第二个 workflow 本身。

### 7.3 已经落进代码/PLAN 的结论

1. 结构化输出用 `instructor` 三档降级，不引中间层框架（多夹一层会让端点能力探测失真）。
2. 永不发 `max_tokens`（不提供开关）。
3. 熔断只数「provider 真的坏了」，模型答错不算故障——否则弱模型会被误熔断。
4. 本地模型只当验证器 / 冒烟，不当生产合成器。
5. 多样性靠 tag 组合枚举，不靠温度；泛化性用组合 / 值 / 维度三种留出度量。
6. 判别器输出结构化分数而不是 pass/fail，且判别器自身要被人工金标准评估。

## 8. 用黑盒 API 时，正确性到底靠什么保证

一句话：**把模型的职责压缩到「只写文本」，其余全部交给代码。**

### 8.1 四层防线

| 层 | 谁来保证 | 覆盖范围 | 漏了会怎样 |
|---|---|---|---|
| ① 真值规格 spec | 采样器（纯代码） | 100% | 后面全白搭 |
| ② 金答案推导 | 代码从 spec 反推 | 100% | 标签错，而且事后查不出来 |
| ③ 往返校验 | 代码 `reparse(render(spec))` | 100%（构造式） | 渲染差一格错位，没人知道 |
| ④ 特征核对 / 判别器 | LLM + 人工抽检 | 全量或抽检 | 措辞、可解性、干扰项问题漏网 |

关键在 ①②：**金答案在采样那一刻就定了，模型碰不到它**。模型产出的文本只是「同一份 spec 的
另一种表述」，所以文本写得差不影响标签正确性——这正是黑盒 API 唯一能放心用的位置。

### 8.2 逐条可操作的规则

1. **先定答案，再采样素材**。想控制答案分布就在采样器里控制（例如「都不经过」占 1/4），
   而不是生成一堆再筛掉——事后过滤会同时扭曲分布与多样性。
2. **渲染必须可反解**。从渲染结果重新推出全部答案，逐题与金答案比对。这一步专抓
   「差一格画错」「方向词写反」这类只有人眼才能发现的错。
3. **打乱与转编号写在同一个函数里**，编号在整个管线里只允许出现在这一处。
4. **严格 JSON**。`json` 模块默认放行重复 key、`NaN`、BOM、布尔当整数、`1.0` 当整数——
   每一条都会让「选项数」和「编号」一起错位，必须显式拒绝。
5. **结构校验全量跑，拒绝率必须为 0**。出现任何一条契约失败都当成生成器 bug 去修，
   而不是把那条样本删掉了事。
6. **统计门槛整批把关**。分布超出容差就整批失败，不偷偷补样凑数。
7. **人工抽检每批 30 条**。发现标签错误先定位原因，不只是删掉这一条。
8. **判别器只处理代码查不了的部分**，而且它自己要被人工金标准评估（见 4.2）。
9. **记账到每条样本**。谁（provider / model / key 指纹 / 档位）出的数据要能事后切片，
   否则一旦发现脏数据只能整批丢。
10. **确定性重跑**。同配置 + 同 seed 生成两次必须逐字节一致；做不到说明有隐藏的采样源
    （时间、随机、并发顺序）。
11. **mock 全绿不等于真端点能收**。假客户端不校验参数，漏传 `model` 这类必填项照样过；
    本项目就踩过这一条——单元测试全绿，真打端点直接报「Missing required arguments」。
    每个后端**至少要真打一次最小请求**，并把必填参数写进断言。

### 8.3 黑盒 API 额外放大的风险与对应措施

| 风险 | 为什么黑盒会放大 | 措施 |
|---|---|---|
| 端点偷偷忽略参数 | 第三方中转常无视 `response_format` 还返 200 | 开机探测 + 本地全量校验，不信任自我声明 |
| 模型跑飞 | 推理模型在矛盾提示下 `finish_reason=length`、`content=None` | 不设 `max_tokens`；把这两种收尾当成一等错误处理 |
| 免费额度中途耗尽 | 没有配额查询接口 | 熔断 + 记账 + 断点续跑，重启接着跑 |
| 中途换模型 | 降级链可能换到不同 model | 每条样本记 provider / model；是否允许混用写进配置与 manifest |
| 服务端悄悄变行为 | 同一模型不同时段能力不同 | 探测结果落 run 元数据；**不要跨 run 比较数据质量** |
| 提示词矛盾 | 模型「想一半被砍死」，答案直接空 | 提示词由代码按 spec 渲染，不做自由发挥 |

## 9. 实跑记录：小批量真端点合成（2026-09-25）

拿 `mail` workflow（特征注入式）在真端点上跑小批量，把踩到的坑记下来。
脚本 `tmp/smoke_mail.py`、配置 `tmp/backends.toml`（都不入库）。

### 9.1 端点与模型实测

| 端点 / 模型 | 结果 |
|---|---|
| NVIDIA NIM `openai/gpt-oss-20b` | **可用**。5 个 key 里 3 个 8~25s 正常返回，2 个挂到超时；靠 key 池轮换 + 重试绕过 |
| NVIDIA NIM `meta/llama-3.1-8b-instruct` | 410 Gone（模型已下线）——**模型名会过期，配置里必须能改** |
| Gemini `gemma-4-26b-a4b-it` | 120s 超时（真实渲染提示词 + `json_schema`） |
| Gemini `gemma-4-31b-it` | 500 Internal error |
| Gemini `gemini-3.1-flash-lite` | 503 高负载 |
| Gemini `gemini-2.5-flash-lite` | 2.8s 稳定返回，但**每 key 每模型每天只有 20 次**（`GenerateRequestsPerDayPerProjectPerModel-FreeTier`） |

结论：免费档只够小批量试跑，当不了主力；主力需要一个能长时间稳定返回的端点。

### 9.2 坑一：每日配额和分钟级限流要分开处理

两种 429 的救法完全相反，混在一起会让整批死在第一个 key 上：

- **分钟级限流**（`429 Too Many Requests`）：降速（RPM 减半）就够，**不能退 key**——
  一波限流就把好 key 全扔了；
- **每日配额**（报错正文带 `PerDay` / `per day` 这类标记）：降速**救不回来**，
  必须把这个 key 退场换下一个，否则每条样本都撞同一堵墙。

`jc.backend.provider` 现在按报错正文区分这两类；认不出来时按分钟级处理（保守：
降速最多慢一点，退 key 会白扔一个 key）。

### 9.3 坑二：标签判据必须能从文本反解出来

第一版 `sender_identity` 问「发件人显示的身份与真实来源一致吗」——**从邮件正文根本判不出来**：
一封邮件自称 SecurePass、地址是 `securepass-auth.net`，读者凭什么知道它真不真？
结果 `TraceJudge`（把邮件交回模型重读特征）21 条全挂，整批 0 通过。

修法是把判据**写进文本**，而不是让判别器去猜：

- 渲染规则要求「声称了机构身份的邮件，落款单独写一行『官方域名：<域名>』」；
- 题目的 criteria 改成可操作口径：「显示名声称的机构，其官方域名（落款那行）与发件地址的
  域名一致 → matches；不一致 → forged；落款里没有官方域名 → no_claim」。

同一批里还有「`ask=none`（不索取任何东西）却又有链接」这种自相矛盾的组合——有链接自然
就像在叫人点。修法是规定**链接只写在落款当参考**，正文出现「请点击」这类邀请句只在
`ask=click_link` 时才允许。

改完之后同一条样本可以完美往返：金答案 4 维与反解结果逐字一致，`LinkJudge` 也过。
**教训：判别器拒掉一条时，先怀疑「这个标签在文本里有没有判据」，再怀疑模型。**

### 9.4 诊断必须能看到被拒的文本

`rejected.jsonl` 原先只记 `id / stage / code / reason`，看不到模型写了什么，等于没法查质量。
现在判别阶段与契约校验阶段被拒的行都带上 `state`——判别器拒掉一条时，
「模型到底写了什么」是唯一的诊断线索。

### 9.5 坑三：清单必须**可满足**（注入式合成的第一件事）

smoke-3 一轮反而比上一轮差（1/5）。查下去发现不是模型变差，而是**清单自相矛盾**：

| 症状 | 根因 | 修法 |
|---|---|---|
| 模型吐 `XXXXX` 摆烂 | `lure=none`（通篇不许施压）与 `tone=threatening`（用警告与后果的措辞）同时出现 | 语气维只留语域（formal / friendly / casual / curt），施压信号统一归 `lure` 维 |
| 三封里三封没有链接 | 提示词说「链接写在落款」，却从没要求写落款 | 落款与链接各占一个**独立必填字段**，结构上强制 |
| `ask=click_link` 的样本判不出来 | 清单同时要求「点击链接」和「没有任何链接」，无解 | `features.allow_pair` 取值对约束，交给 `jc.cover` 枚举器表达 |

教训：**提示词里写十遍规则，不如让模型少一个可漏的字段**；而「某个取值组合根本写不出来」
这种约束要放进枚举器，不能事后过滤（实测直接过滤会漏掉 4 个允许的取值对）。

### 9.6 坑四：单选判别器看不出「夹带」

数据里那道「要收件人做什么」是单选，但文本可以同时提出两种索取——实跑抓到过
「清单只要求打开附件，正文却写『请按提示输入密码』」，四个原子题全答对，样本照样混进去。
修法是反解时**多问一道多选**（`TraceDraft.extra_requests`），有夹带就丢掉。

同一类盲区还有**格式损坏**：落款末尾多一个 `}`、落款里一串 `<br>`，两种情况下语义判别器
都答对了；后来还抓到第三种——落款里连着两个「官方域名：」（`render.to_state` 会追加那一行，
模型又把同样的行写进了 `signature`，35 条真端点样本里中过 2 条）。补一个零 token 的
`HygieneJudge` 只查格式残留——口径压到最窄，因为误判会直接拒掉好数据。
行首标记从 locale 模板推出来，所以换语言照样认得出。

### 9.7 各轮合格率（NIM `openai/gpt-oss-20b`）

| 轮次 | 样本 | 合格 | 当轮暴露的问题 |
|---|---|---|---|
| smoke-2 | 5 | 2 | 手法四档的互斥口径没生效；`mismatched` 只写一个地址 |
| smoke-3 | 5 | 1 | 语气维与手法维撞车；提示词没要求写落款 |
| smoke-4 | 6 | 4 | 判据重叠（`credentials` 与 `payment` 都含「卡号」）；`click_link` 配 `link=none` 无解 |
| smoke-5 | 6 | 3 | 「不索取」清单下仍写「请点击此链接」；落款末尾多一个 `}` |
| smoke-6 | 6 | 2 | 落款字段填了但链接整块漏掉；`fear` 判据把「发现异常」也算后果 |
| smoke-7 | 6 | 5 | 落款里一串 `<br>` |

**合格率不是纯质量指标**：判别器和生成器是同一个模型，两边都会误判
（smoke-6 有一条只给时间窗、没描述任何后果的邮件被反解成 `fear`，那是判别器误判）。
要分开衡量得靠人工复核被拒样本，这一步现在还是手动的。

### 9.8 坑五：挂死是**模型级**的，不是端点级也不是 key 级

smoke-8 有 3 条样本记成 `E_ASSEMBLE：全部 provider 都不可用`，一轮跑了 56 分钟。
逐项验过之后，根因不是端点、不是 key：

| 验的东西 | 结果 |
|---|---|
| `GET /v1/models` | **200，0.7 秒**（端点活着） |
| `POST /chat/completions`，`openai/gpt-oss-20b`，5 个 key 逐个打 | **5 个全在 45 秒超时**，curl 原始请求 120 秒连 header 都不回 |
| 同一个 key 换 `z-ai/glm-5.3-flash` | **秒回**，`nvidia/nemotron-3.5-lightning-30b-a3b`、`moonshotai/kimi-k3` 同样秒回 |
| `stream: true` 打 `gpt-oss-20b` | 照样挂死（不是「非流式才不吐字」） |

**结论**：超时重试救不了模型级挂死，只会把时间烧在同一个死模型上（每次超时都是白等一个
`timeout_s`）。正确做法是**降级换模型**，而且熔断阈值要压小（超时 60 秒 + 连续 3 次就跳闸），
否则一个挂死的模型能把整批拖成一个小时。

附带一个坑：**`/v1/models` 列出来的模型 ≠ 这个账号能调的模型**。不能调的返回
`404 Function '...' Not found for account`，得单独探一遍才能知道哪几家真能用。

### 9.9 坑六：熔断器把调用锁在临界区里，并发配置形同虚设

smoke-8/9/10 一轮要跑 50~90 分钟（只有 8 条样本）。查的过程中先后怀疑过「key 烧干了」
「模型挂死了」，逐条验掉之后都不是，最后用 `py-spy dump` 拍下跑着的进程才一眼看清：

| 线程 | 卡在哪 |
|---|---|
| worker 0 | 真在发请求（`httpx` → `ssl.read`） |
| worker 1~4 | `pybreaker/__init__.py:250` 的 `with self._lock` |

`pybreaker.CircuitBreaker.call()` 的实现就是 `with self._lock: return self.state.call(func, ...)`，
**被保护的调用整个在锁里**。于是同一个 provider 的请求被串行化，配的
`max_concurrency=5` / `max_concurrency_per_key=1` 全不作数——实测并发恒为 1。

教训：

- 熔断需要的互斥是**状态判定与状态转换**，不是调用本身。换成 59 行的自研 `Breaker`
  （锁只护状态机、调用在锁外）之后，同一批立刻看到 **5 条并发连接**；
- 顺手把「第 `fail_max` 次失败」改回**原样抛真实异常**：pybreaker 的
  `throw_new_error_on_trip` 会把它替换成 `CircuitBreakerError`，日志里就看不到真原因了；
- 守门测试要**直接测并发行为**：并发跑 N 个「放行 → 占位 0.15 秒 → 记账」，断言峰值并发 = N。
  旧实现下峰值恒为 1，这条测试必然失败。**库的并发行为要自己测，文档不会告诉你**。

排查手法本身也值得记：`py-spy dump --pid <pid>` 比加日志快得多，一次定位，
不用为了看状态去改代码重跑（一轮就是几十分钟）。

### 9.10 坑七：「整批全被拒」不是数据质量问题，是基础设施噪声

smoke-9 的 8 条样本全被拒，其中 7 条的拒绝码是 `E_ASSEMBLE：全部 provider 都不可用`。
当时的实现把「全挂」当成「这条样本没通过」，于是整批照跑到底，产出一个
**看上去正常、其实全是拒绝**的 run；合格率「0/8」会被读成「合成质量崩了」。

修法：

- 错误自己声明 `fatal_for_run`（`AllProvidersDown` 声明为真），判别器不再把它吞成「这条没过」；
- 管线遇到它**中止整批**，但**先把已合格的产物落盘**，再抛 `RunAborted`（带 `accepted` 与 `run_dir`）；
- 算合格率时，`E_ASSEMBLE` 这类行必须从分母里剔除，否则数字会骗人。

同一类问题的另一半是**串行编排**：管线原来是 `for seq in range(total)` 一条条跑，
后端的并发闸再宽也用不上（一轮 8 条 = 8 个 case 的调用时间之和）。补上 `concurrency` 之后，
「并发可配」才真的可配。

### 9.11 坑八：「都给不出合格草稿」被当成「全都挂了」

- 现象：`moonshotai/kimi-k3` 跑 6 条，前 4 条正常合格，第 5 条起整批中止，
  报「全部 provider 都不可用」；日志里夹着
  `Max retries exceeded. Total attempts: 1, Last error: list index out of range`。
- 现场：`instructor` 在 `tools` 档拿不到 `tool_calls` 时会抛 `IndexError`，并在
  `instructor/v2/core/retry.py` 里包成 `InstructorRetryException` 抛出（那句
  `Max retries exceeded` 是**它**打的日志，跟 `max_tokens` 无关）。我们的分类把它归到
  `DraftInvalidError`（这一步是对的），但后端链把「草稿不合格」和「这家挂了」都记成
  「换下一家」，全都没成时统一抛 `AllProvidersDown`（`fatal_for_run=True`）→ 整批停下。
- 判据：`AllProvidersDown` 的语义是「provider 挂了」（熔断 / key 用尽 / 网络），
  「模型答非所问」不属于它。端点健康是当场验过的：同一个模型、5 个 key、极小请求全部秒回。
- 修法：`DraftInvalidError` 不再参与「换下一家」的记账，单独记住；只有**一家都没活着**
  才抛 `AllProvidersDown`。全都活着但都给不出合格草稿时抛 `DraftInvalidError`，
  由管线记成这一条被拒、整批继续跑。
- 教训：**「不可用」要按判据定义，不能按心情定义**——把样本级失败升级成批次级失败，
  代价是白扔已经跑好的进度和配额。顺带一条：跨模型对照跑（glm → kimi）本身有价值，
  它验出「提示词 + 判别器不是某一个模型专属」，也把这个只在 kimi 上暴露的路径炸了出来。

### 9.12 坑九：「全都挂了」被当成「都给不出合格草稿」

- 现象：NIM 的 `z-ai/glm-5.3-flash` 小批量跑 3 条，2 条被拒，拒绝码却是
  `E_ASSEMBLE：模型没给出合格草稿：Request timed out.`；同批日志里还夹着 `Error code: 504`。
  端点当时明显是**服务端故障**，却被记到了「模型不行」的账上。
- 根因：`instructor` 把**任何**打光重试的异常统一包成 `InstructorRetryException`
  （`raise ... from last_exception`），我们的分类见到它就一律给 `DraftInvalidError`
  （`counts_as_fault = False`）。于是读超时 / 504 既不被 tenacity 重试、也不计熔断、
  也不触发 provider 降级，还把「端点挂了」写成了数据质量问题——一次 600 秒的读超时
  就这样被当成一次「模型答错」。
- 与 9.11 的关系：这两坑是**同一句话的两个方向**。9.11 是「草稿不合格」被升级成
  「全都挂了」（批次级误杀）；这里是「全都挂了」被降级成「草稿不合格」（故障被吞掉）。
  判据是同一条：**先看底层原因，再决定它属于哪一级**。
- 修法：`classify_exception` 遇到 `InstructorRetryException` 先沿 `__cause__`
  （缺失则退回 `failed_attempts[-1].exception`）还原底层异常再分类——认证 / 限流 /
  schema 不支持 / 网络与 5xx 原样上抛（该退 key、该降速、该降档、该重试换家），
  只有底层真是校验 / 解析失败才归 `DraftInvalidError`。沿链走到底并记已访问的 id，
  嵌套与自引用都不会递归失控。
- 顺带：`InstructorRetryException.failed_attempts` 里留着每次尝试的原始异常，是排查这类
  问题的第一手证据；日志里那句 `Max retries exceeded` 跟 `max_tokens` 无关（见 5.2）。
