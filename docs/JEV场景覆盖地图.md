# JEV 场景覆盖地图

> 目标：把 awesome-jev 收录的社区项目按**场景簇**归堆，与本仓库已发布的 51 家 workflow 对齐，
> 给出「已覆盖 / 部分覆盖 / 没覆盖」三态，并列出下一步该造哪几家、按什么顺序造。
>
> 数据来源：awesome-jev 的 README 表格（**2026-10-01 抓的 965 条**，字段：名字 / ★ / 语言 /
> 收录日期 / 中文描述）。分桶用「关键词表 + 人工归位表」，一条可落进多簇。

## 1. 方法与口径

- 分桶是**关键词正则 + 人工归位**，不是逐条标注：描述里出现「工具调用」就落进工具簇。所以一个
  项目常落进多簇（它既有工具、又有场景），29 簇条数之和 **979** 远大于场景总数 **625**——别拿
  簇条数之和当分母。
- 关键词一条都没命中的有 **200 条**，已逐条人工归位：**128 条本来就属于已有场景簇**（只是词表
  没覆盖到），**72 条是工具 / 适配器 / 插件 / 演示 / 模型权重 / 校准与评测脚本**——不描述任务
  场景，归基础设施。归位后：**基础设施 340 + 场景 625**（关键词判 268 + 人工判 72）。
- 「覆盖」判的是**任务形状**（问什么、答案从哪来），不是关键词撞车。例：`jev-search` 与我们的
  `search` 都提「搜索」，但它问的是「选哪个来源」，我们问的是「这条结果可不可信」——两个任务。
- 判据表里「状态」三档：**覆盖**（同一个任务形状已经有 workflow）／**部分**（同一族但少一个
  关键轴）／**缺口**（没有对应的 workflow）。

## 3. 缺口清单（按「标签能不能算出来」排序）

排序口径就是本仓库的第一原则（范式 §0）：**标签是算出来的还是问出来的**。A 档能算、B 档能算
但要有素材、C 档只能问模型（不做）。

### A 档：纯构造式，零 token

1. **片段筛选与去冗余**（**已做**：第 44 家 `clipcut`，2026-09-30 发布）（`summarize` ★223 /
   `jevmeter` ★70 / `jevclip` ★21）——给一串带序号的
   片段，判「哪几段保留」。保留规则可写成纯函数：**有高亮点** 且 **主题没在更靠前的保留片段里
   出现过**（先到先得）。这一族带来一个我们还没有的轴：**顺序折叠**——`cachereuse` 只做前缀对齐，
   保留集却是「从前往后扫、见到重复就丢」的累积过程，答案依赖**前缀**而不只是本条。
2. **金融读数判读**（**已做**：第 45 家 `quoteread`，2026-09-30 发布）（`TradingAgents`
   ★108478 的相关性/情绪筛选、`Jev-X-Sentiment-Analysis` ★162、`jevocks` ★9）——给一份行情
   读数表（代码写），判「涨跌幅落在哪一档」「有没有触发某条阈值」「哪个标的涨得最多」。带来
   **量纲 / 单位换算 + 档位** 这个轴：`receiptcat` 是同量纲比上限，这里是「先把百分比换算成
   基准点再比」，多一步算术。
3. **界面元素定位**（**已做**：第 48 家 `elementpick`，2026-09-30 发布）（Jev Ultrafast ★9291
   「在一次请求中选择操作和 DOM 元素」/ `agent-desktop` ★1441 / `surf-cli` ★624 / `Jev-cu`
   ★584）——给一份元素清单（代码写的角色 / 可见性 / 可点性 / 文本），判「这个动作落在哪个
   元素上」。与 `browser` 的区别是：`browser` 问「下一步做什么动作」（要读一串历史、判动作
   序列与完成度），这里问「**这个动作落在哪个元素上**」，是纯查表。带来一个我们还没有的
   轴：**「唯一解」代替「按顺序取第一个」**——同名元素里恰好一行可见且可点，所以判据不需要
   任何「谁更靠上」的约定（环形排布下那条约定根本不成立，见范式 §9.79 第一条）。

### B 档：注入式（结构由代码写、文本由模型写）

4. ~~**候选回复挑选**（`jev-chat-jarvis` ★1696 / `jev-yaba-wechat` ★17）~~ —— **已覆盖，不用做**：
   `chatgate` 的 `reply` 那一族就是「三条候选回复里该发哪一条」（答案由候选自己的毛病算出来），
   本条原先写的「`chatgate` 没有这一族」是**错的**。残留的小缺口只有「**逐条**判该不该发」
   （而不是在三条里挑一条），那只是同一张毛病表的另一种问法，不值得单开一家。
5. **来源选择**（`jev-search` ★244「来源选择、查询理解」）——给一条查询与一张候选来源表
   （代码写的权威度 / 时效性 / 类型），判「该用哪个来源」「够不够权威」。`search` 判的是「这条
   结果可不可信」，**没有「先选源」**这一步。
6. ~~**改动引入性判定**（`celesto` ★958「判断调查结果是否被引入、支持和可操作」）~~ —— **已覆盖**：
   第 47 家 `findtriage` 就是它。给一条审查发现 + 一份改动记录，判「这个发现是本次改动引入的吗」
   「有证据支持吗」「可执行吗」。三轴正交，正是 `review` 缺的「引入性」那一维。

### C 档：不做

7. ~~**根因分析**（`Stratum` ★51）~~ —— **已覆盖**：第 51 家 `causechain`（2026-10-01）。
   原先判它「只能问模型」是因为把「根因」当成对一段自然语言日志的**语义**结论；把**依赖图**
   与**三种事件形状的判据**当成注入特征（由代码写进 state）之后，根因 = 出错服务里没有任何
   出错下游的那一个，**从文本按字面算得出来**——这一条改判的依据就在这里，见范式 §9.90。
8. **主观风格润色 / 语气改写**——同上。

## 5. 下一步

社区侧已经清点完了：**没有未判的簇，也没有未归类的条目**（§1 / §4）。2026-10-01 重抓的
965 条里新涨 49 条，逐条看过：**46 条落在已有簇**，2 条关键词没命中但已归位（`FluidUse` 的
「从辅助功能状态选表单动作」→ `elementpick` 的查表形状；`1 Million Emojis` 的「选下一格画什么」
→ `sim` / `maze` 的格子形状）。

**唯一一个值得单说的新条目是 `Tiltmeter`**（★0，类别「框架与集成」）：它记录决策模型的读数，
对「模型版本变化 / 分布漂移 / 阈值拥挤 / 估计准确率下降」四种情况告警。**判定：不做**，
理由是它判的对象是**概率读数的分布**，而本仓库的口径是「答案只有 choice / noul / score、
不做概率输出」——把概率分布当输入，等于要求产物里带概率，与第一原则冲突。
它的四种判断本身都能算（窗口对基线的计数比较），所以**真要做得先改口径**，不是加一家能解决的。
这条**如实记在这里，不偷偷划掉**。

再往前只有一条路——往已有的 51 家里加题族，而不是新开一家。**2026-10-01 先做了一家**：
`causechain` 从四族加到五族，新增 `count`（受影响服务数，**score 题**，这一家唯一的 score 族，
`kinds` 从 `choice/noul` 变成 `choice/noul/score`）。同一批候选里的「哪一跳断了」**试过之后
不加**——本 workflow 的传播模型里它等价于「断在哪个服务」，化归成 `root` / `hop` / `isroot`
已经在问的（判据见范式 §9.92）。真机复验：`cc-10c-zh` / `cc-10c-en` 各 10 条、收 10 拒 0、
三个判别器全过、审计零缺失。

**同日第二家**：`findtriage` 从六族加到七族，新增 `owner`（这条发现该进谁的队列，choice 四档）。
原先记的候选描述（「在 state 里多印一张『谁负责哪类文件』的归属表」）**与这一家的记录表对不上**
——它的记录表只有「序号 / 行号 / 本次改动 / 符号」四列，没有文件路径那一列，要按文件类型归属
得先改表格式（会连着 render / 判别器 / 审计一起动）。所以改成按**可判的三件事**归属
（指向的行在不在表里 × 引用符号在不在表里 × 那一行本次碰过没有），口径印进 state 第五段。
真机：`ft-10a-zh` 收 10 拒 0、`ft-10b-en` 收 7 拒 3（3 条全在反解读者身上，产物审计零缺失）。
两家的判据与踩坑见范式 §9.92 / §9.93。
