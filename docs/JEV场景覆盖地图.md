# JEV 场景覆盖地图

> 目标：把 awesome-jev 里的社区项目按**场景簇**归堆，与本仓库已发布的 48 家 workflow 对齐，
> 给出「已覆盖 / 部分覆盖 / 没覆盖」三态，并列出下一步该造哪几家、按什么顺序造。
> 数据来源：`tmp/docs/awesome-jev.rows.json`（916 条，字段：名字 / ★ / 语言 / 收录日期 / 中文描述）
> 复现脚本：`tmp/scene_map.py`（关键词分桶；一条可落进多簇）
> 写作日期：2026-09-30

## 1. 方法与口径

- 分桶是**关键词正则**，不是人工标注：描述里出现「工具调用」就落进工具簇。所以一个项目常落进
  多簇（它既有工具、又有场景），各簇条数之和远大于 916。
- 273 条（30%）一条簇都没落进——多是 SDK / 适配器 / 模型权重 / 榜单这类**基础设施**，它们
  不描述任务场景，本来就不该进场景簇。这 30% 与本项目无关（我们不发布 SDK）。
- 「覆盖」判的是**任务形状**（问什么、答案从哪来），不是关键词撞车。例：`jev-search` 与我们的
  `search` 都提「搜索」，但它问的是「选哪个来源」，我们问的是「这条结果可不可信」——两个任务。
- 判据表里「状态」三档：**覆盖**（同一个任务形状已经有 workflow）／**部分**（同一族但少一个
  关键轴）／**缺口**（没有对应的 workflow）。

## 3. 缺口清单（按「标签能不能算出来」排序）

排序口径就是本仓库的第一原则（范式 §0）：**标签是算出来的还是问出来的**。A 档能算、B 档能算
但要有素材、C 档只能问模型（不做）。

### A 档：纯构造式，零 token

1. **片段筛选与去冗余**（**已做**：第 44 家 `clipcut`，2026-09-30 发布）（`summarize` ★223 /
   `jevmeter` ★70 / `jevclip` ★21）——给一串带序号的
   片段，判「哪几段保留」。保留规则可写成纯函数：**有高亮点** 且 **主题没在更靠前的保留片段里
   出现过**（先到先得）。这一族带来一个我们还没有的轴：**顺序折叠**——`cachereuse` 只做前缀对齐，
   保留集却是「从前往后扫、见到重复就丢」的累积过程，答案依赖**前缀**而不只是本条。
2. **金融读数判读**（**已做**：第 45 家 `quoteread`，2026-09-30 发布）（`TradingAgents`
   ★108478 的相关性/情绪筛选、`Jev-X-Sentiment-Analysis` ★162、`jevocks` ★9）——给一份行情
   读数表（代码写），判「涨跌幅落在哪一档」「有没有触发某条阈值」「哪个标的涨得最多」。带来
   **量纲 / 单位换算 + 档位** 这个轴：`receiptcat` 是同量纲比上限，这里是「先把百分比换算成
   基准点再比」，多一步算术。
3. **界面元素定位**（**已做**：第 48 家 `elementpick`，2026-09-30 发布）（Jev Ultrafast ★9291
   「在一次请求中选择操作和 DOM 元素」/ `agent-desktop` ★1441 / `surf-cli` ★624 / `Jev-cu`
   ★584）——给一份元素清单（代码写的角色 / 可见性 / 可点性 / 文本），判「这个动作落在哪个
   元素上」。与 `browser` 的区别是：`browser` 问「下一步做什么动作」（要读一串历史、判动作
   序列与完成度），这里问「**这个动作落在哪个元素上**」，是纯查表。带来一个我们还没有的
   轴：**「唯一解」代替「按顺序取第一个」**——同名元素里恰好一行可见且可点，所以判据不需要
   任何「谁更靠上」的约定（环形排布下那条约定根本不成立，见范式 §9.79 第一条）。

### B 档：注入式（结构由代码写、文本由模型写）

4. ~~**候选回复挑选**（`jev-chat-jarvis` ★1696 / `jev-yaba-wechat` ★17）~~ —— **已覆盖，不用做**：
   `chatgate` 的 `reply` 那一族就是「三条候选回复里该发哪一条」（答案由候选自己的毛病算出来），
   本条原先写的「`chatgate` 没有这一族」是**错的**。残留的小缺口只有「**逐条**判该不该发」
   （而不是在三条里挑一条），那只是同一张毛病表的另一种问法，不值得单开一家。
5. **来源选择**（`jev-search` ★244「来源选择、查询理解」）——给一条查询与一张候选来源表
   （代码写的权威度 / 时效性 / 类型），判「该用哪个来源」「够不够权威」。`search` 判的是「这条
   结果可不可信」，**没有「先选源」**这一步。
6. ~~**改动引入性判定**（`celesto` ★958「判断调查结果是否被引入、支持和可操作」）~~ —— **已覆盖**：
   第 47 家 `findtriage` 就是它。给一条审查发现 + 一份改动记录，判「这个发现是本次改动引入的吗」
   「有证据支持吗」「可执行吗」。三轴正交，正是 `review` 缺的「引入性」那一维。

### C 档：不做

7. **根因分析**（`Stratum` ★51）——「根因」不是从表里算得出来的，只能问模型，正是范式 §0 说的
   D 档。做出来也只是一堆看起来像答案的文本。
8. **主观风格润色 / 语气改写**——同上。
