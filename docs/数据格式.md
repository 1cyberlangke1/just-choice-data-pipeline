# 数据格式（JSONL 契约）

产物是 JSONL：**一行一份记录，一份记录带整组题**。同一份记录里的题共享一个 `state`（题面上下文），
答案放在 `answers` 里，题号是 `questions` 的 key。契约层是 `src/jc/contract.py`，校验器是
`src/jc/validate.py`——本文说的每条约束都有对应的错误码。

## 一、文件布局

一次生成产出一个目录（run），里面长这样：

```
<run_id>/
  train.jsonl           训练切分，一行一份记录
  val.jsonl             验证切分
  test_iid.jsonl        同分布测试切分
  test_ood.jsonl        留出测试切分
  manifest-<切分>.json   这一份产物的声明与统计（workflow / 语言 / 后端 / 判别器 / 计数）
  calls-<切分>.jsonl     逐条来源：provider / 模型 / key 指纹 / 重试次数 / token 用量
  stats-<切分>.md        统计的人读版
  progress-<切分>.jsonl  断点续跑的进度日志
  rejected.jsonl         被判别器拒掉的草稿，**不进** `train.jsonl`
  judge-skipped.jsonl    端点故障导致「没判成」的样本，**不进** `train.jsonl`
```

四份 `*.jsonl` 才是数据；其余是随产物一起落的账，用来回答「这条是谁写的、为什么被拒」。

## 二、顶层字段

一份记录**只允许**四个字段，多一个即不合格（`E_FIELD_UNKNOWN`），少一个也报错（`E_FIELD_MISSING`）：

| 字段 | 类型 | 是什么 |
|---|---|---|
| `id` | string | `{workflow}-{切分}-{序号:07d}`，例如 `maze-train-0000042`；一份产物内唯一 |
| `state` | string | 题面上下文（渲染出来的那一屏）。同组题共享；模型写的那部分文本也在里面 |
| `questions` | object | 题号 → 题目对象。题号就是题族名（同族多题时带后缀） |
| `answers` | object | 题号 → 答案对象，键与 `questions` 一一对应 |

`id` 的形状被契约钉死：`^[a-z][a-z0-9_]*-(train|val|test_iid|test_ood)-\d{7}$`。

## 三、题目对象

每道题**只允许**三个字段（`E_Q_FIELD_UNKNOWN` / `E_Q_FIELD_MISSING`）：

| 字段 | 类型 | 是什么 |
|---|---|---|
| `type` | string | `choice` / `noul` / `score` 三者之一 |
| `instructions` | string \| object \| array | 问法。按语言或问法轮转时可以写成 object / array |
| `criteria` | object \| array \| 省略 | 选项表，见下 |

## 四、三种题型

| 题型 | 答案是什么 | `criteria` | 答案字段 |
|---|---|---|---|
| `choice` | 答案是**选项** | 对象 `选项名 → 描述`；某个选项写成 `null` 表示「这个选项没有描述」 | `choice`：选项下标，**从 0 开始** |
| `noul` | 答案是 true / false | 可省略；写了必须是对象，且**只允许** `true` / `false` 两个键 | `noul`：JSON 布尔 |
| `score` | 答案是整数评分（例如 1~5 档） | 数组，等级描述；**不允许** `null`（等级描述就是等级定义） | `score`：等级下标，**从 0 开始** |

答案对象同样只允许 `type` 加一个值字段，例如 `{"type": "choice", "choice": 2}`。
描述值的形态只允许 string / object / array / null（`E_DESC_TYPE`）。

数量约束：`choice` 要 2~255 个选项，`score` 要 2~10 个等级。

## 五、编号口径（最容易踩的一条）

`answers.choice` 与 `answers.score` 是**这一条自己的 `criteria` 里的书写顺序**下标，从 0 开始。
有的 workflow 会按样本打乱选项顺序，所以：

- 不要跨记录复用下标；
- 不要按自己重排的顺序去数；
- 想把编号换回选项名或描述，就按这一条的 `criteria` 现读。

上游 [Open-Jev](https://huggingface.co/datasets/ZefanCai/Open-Jev) 存的是与选项对齐的**概率向量**；
本仓库刻意改存**编号**——不做概率、不做置信度，下游要概率自己算，管线不替它猜。

## 六、一条真实记录（`state` 截断）

```json
{
  "id": "routing-train-0000000",
  "state": "【工单正文】请问在 DemoApp 中如何正确使用 XYZ 功能……\n【工单属性】（产品域 | 客户等级 | 合规标记）\n- analytics | enterprise | security\n…",
  "questions": {
    "issue": {
      "type": "choice",
      "instructions": "这条工单属于哪一类问题？",
      "criteria": {
        "bug": "缺陷：行为与文档写的不一样",
        "outage": "故障：某条线整体不可用",
        "howto": "咨询：问正确用法",
        "data_loss": "数据丢失：记录少了 / 对不上",
        "feature": "需求：想要一种新做法"
      }
    }
  },
  "answers": { "issue": { "type": "choice", "choice": 2 } }
}
```

这条的答案是 `choice: 2`，按 `criteria` 的书写顺序数是第三个选项 `howto`——**不是**按字母序，
也不是按你自己重排的顺序。

## 七、怎么校验

契约检查在生成期与审计期都会跑，报错给到具体错误码与字段路径：

```powershell
python -m jc audit --workflow routing --dir dataset/routing-train --split train
```

会拦的东西包括：字段多余或缺失、类型不对、编号越界、`noul` 不是 JSON 布尔、`score` 等级含 `null`、
`id` 形状不对，以及行级的 BOM、重复键、`NaN`。
